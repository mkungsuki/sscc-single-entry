# nRefer: ผลตรวจและแผนเดินต่อ

วันที่ 2026-09-09 — ตรวจจาก working tree ปัจจุบัน ไม่ได้แก้ production code/config หรืออ่านฐานเคสจริง

## ข้อสรุป

**Fix-then-ship: ยังไม่พร้อมใช้งานจริง** เพราะการยืนยันว่าบันทึกสำเร็จยังผูกกับครั้งรักษาไม่ได้ และเส้นทางส่งซ้ำยังเปิดรายการใหม่ แม้แก้ ThaID ได้ก็ยังมีปัญหานี้

เป้าหมายคือกรอกจาก SSCC ลงฟอร์ม nRefer แล้วหยุดให้พยาบาลตรวจและกดบันทึกเอง การคงแนวทาง browser form filling เดิมเหมาะกับเป้าหมาย ไม่จำเป็นต้องรื้อเป็น API integration หรือสร้าง browser service ใหม่ทันที

ทางเลือกที่เล็กกว่า: รุ่นแรกทำทีละเคส, เคสที่เคยส่งเปิดเพื่อค้น/ตรวจบนทะเบียน, ห้ามสร้างใหม่อัตโนมัติจากปุ่มส่งซ้ำ, สถานะไม่แน่ชัดให้ตรวจทะเบียนก่อน retry ส่วน session ตลอดวันและ edit automation ค่อยทำเมื่อพิสูจน์ว่าจำเป็น

## Findings เรียงตามความสำคัญ

### F1 — P1: การยืนยันสำเร็จและ ref ไม่ผูกกับเคส/ครั้งรักษา

- หลักฐาน: `app/fill_nrefer.py:225–267` รับทุก response ที่ URL มี `/dmis/imc/save-patient` และ status สำเร็จ โดยไม่ตรวจ request payload, HN, AN, hospcode หรือ ref จากรายการที่ผู้ใช้กดบันทึก แล้วค้นด้วย HN+hospcode และเลือก `max(refs)`
- เส้นทาง: `process_case → wait_for_save → db.set_nrefer` ที่บรรทัด 301–303; หากผู้ใช้เปลี่ยนไปบันทึกเคสอื่นในหน้าเดียวกันก็เข้าเงื่อนไขได้ การแก้ admission เก่าที่ ref ต่ำกว่ารายการอื่นของ HN เดียวกันจะจับ ref ผิด
- พิสูจน์ออฟไลน์: response จำลองไม่มีข้อมูลผูกเคส และผล query มี AN CURRENT/ref 11 กับ OTHER-VISIT/ref 99; ฟังก์ชันคืน saved=True/ref=99
- แก้ขั้นต่ำ: ติด listener ก่อนเปิดให้ตรวจ; ตรวจ origin/path/method และ request identity เทียบเคส; ใช้ ref ที่ยืนยันได้จาก response หรือ exact lookup hospcode+HN+AN; หลายผลลัพธ์/ไม่มี AN/identity เปลี่ยนต้องเป็นสถานะต้องตรวจสอบ ห้ามเดา ref สูงสุด
- บรรทัด 307 ยังกล่าวว่า “ไม่มีอะไรถูกบันทึก” เมื่อไม่พบผลตอบกลับ ทั้งที่ response อาจสูญหายหรือหมดเวลาระหว่างบันทึก ควรบอก “ยังยืนยันผลไม่ได้” และให้ตรวจทะเบียนก่อน retry

### F2 — P1: ส่งอีกครั้งสร้างรายการใหม่ และ UI เรียกว่าอัปเดต

- หลักฐาน: `app/fill_nrefer.py:280–283` แจ้งเตือนแล้วเรียก `open_add_form` เสมอ; `app/server.py:290–297,331–352` ไม่มีการกันเคสมี ref หรือ deduplicate case_ids
- `app/templates/form.html:394` เปลี่ยนข้อความเป็น “ส่ง nRefer อีกครั้ง (อัปเดต)” แต่ไม่มี update flow
- ผลกระทบ: เคสเดิมหรือ ID ซ้ำในคิวถูกนำไปกรอก Add new อีกครั้ง; AN ว่างยิ่งไม่มีเกณฑ์จับคู่ที่โปรแกรมยืนยันได้ การเตือนของเว็บยังไม่ใช่หลักฐานว่าไม่มีข้อมูลซ้ำ
- แก้ขั้นต่ำ: มี ref แล้วเปลี่ยนเป็นเปิดทะเบียนเพื่อตรวจ/แก้เอง; ห้าม Add new ผ่านเส้นทางเดิม; deduplicate คิว; กำหนดนโยบายเคสไม่มี AN ให้พยาบาลตรวจรายการเดิมก่อนสร้าง

### F3 — P1: mapping สร้างค่าที่ต้นทางไม่ทราบ และมีความหมายข้อมูลไม่ตรงกัน

- `app/nrefer_map.py:187,267`: ไม่มีเลขบัตรประชาชน → เอา HN ใส่ `editRow.person_id` จริง
- `app/nrefer_map.py:59–68,278–285`: มีวันที่แต่เวลาไม่มี/รูปแบบไม่ตรง → กรอก `00:00` โดยไม่แจ้งว่าเวลาไม่ทราบ
- โพรบยืนยันทั้งสองพฤติกรรมด้วยข้อมูลสมมติ
- `app/schema/sscc_fields.json:2346` ระบุ C5 เป็น CT และ/หรือ MRI/MRA ภายใน 24 ชั่วโมง แต่ `app/nrefer_map.py:146–147` แปลงเป็น CT Scan ได้ทำโดยตรง; จาก source field เพียงตัวนี้ไม่สามารถแยก MRI-only ออกจาก CT ได้ และค่าไม่ได้รับภายใน 24 ชั่วโมงก็ไม่ได้ยืนยันว่าไม่เคยทำ CT เลย
- `app/nrefer_map.py:165–172` มีวันที่จำหน่ายก็ใส่ทุเลา และ EMS/ambulance แบบไม่แยกหน่วยงานก็เลือก EMS รพ. เป็นข้อสมมติ ไม่ใช่ข้อมูลยืนยัน
- แก้ขั้นต่ำ: missing ต้องคง unknown/ว่างพร้อมรายการให้ผู้ใช้เติม; ไม่ใช้ HN แทนเลขประชาชน; เวลาที่ขาดไม่แต่งขึ้น; clinical mapping CT/ผลจำหน่าย/EMS/TIA/CVT ต้องมีเจ้าของข้อมูลรับรองก่อนเปิดใช้ การตรวจครั้งนี้ไม่ได้ตัดสินรหัสทางคลินิกแทนเจ้าของทะเบียน

### F4 — P1: กรอกเสร็จโดยไม่ตรวจค่ากลับ และข้อมูล HIS อาจค้าง/ทับ

- `app/fill_nrefer.py:164–171` รอ HIS ด้วยเวลาตายตัว 1.5 และ 1 วินาที; บรรทัด 179 ข้ามค่าข้อความว่าง, วันที่ไม่มีไม่ถูกล้าง; `set_date` บรรทัด 125–133 ตรวจแค่ว่า dispatch สำเร็จ
- โพรบที่ใส่ค่าค้างในช่องโทรแล้วส่งต้นทางว่างยืนยันว่าค่าค้างยังอยู่ ส่วน HIS ที่ตอบช้ายังไม่ได้ทำซ้ำกับเว็บจริง
- บรรทัด 286–300 เก็บ warnings ลง log แล้วขึ้นแถบสีเขียวให้ตรวจและบันทึก โดยไม่ยืนยันค่าแบบ readback
- แก้ขั้นต่ำ: รอ readiness ของการค้น HIS, แสดงที่มาของค่าที่ HIS เติมและนโยบายกรณีขัดกับ SSCC; อ่านค่าที่กรอกกลับเทียบ; critical mismatch เช่น identity/date ต้องหยุดแสดงว่าพร้อมบันทึก; ช่องอื่นแสดงรายการ unresolved บนหน้าตรวจ
- ไม่ควรล้างข้อมูล HIS ทุกช่องโดยไม่กำหนดนโยบายก่อน เพราะบางค่าอาจถูกต้องและมีประโยชน์

### F5 — P1: auto-confirm ของ mock อยู่ในโปรแกรมจริงและตรวจ URL ด้วย substring

- `app/fill_nrefer.py:337–340`: URL ใดมี `localhost` หรือ `127.0.0.1` จะผ่าน mock guard แม้ hostname เป็นโดเมนภายนอก; `process_case:289–290` กดบันทึกเองได้
- โพรบยืนยันว่า `https://example.invalid/?next=localhost` ถูกจัดเป็น mock; ไม่ได้เปิด URL หรือกดบันทึกจริง และยังไม่ได้ทดสอบ redirect end-to-end
- แก้ขั้นต่ำที่ตรงหลัก handoff ที่สุด: ย้ายการคลิกบันทึกอัตโนมัติออกไปอยู่ test harness เท่านั้น ตัวกรอก production ไม่มีทางเลือก auto-confirm; harness ใช้ exact loopback origin และไม่อนุญาตออกนอก mock รวมถึง redirect

### F6 — P2: readiness ของ login เชื่อแค่ token ไม่ใช่สถานะ authenticated จริง

- `app/fill_nrefer.py:51–69,96–101`: parse JWT ไม่ได้คืน `{}`; ไม่มี exp ถูกถือว่าใช้ได้; ยัง fallback ไป localStorage
- โพรบยืนยัน `token_ok('not-a-jwt') == True`
- แก้ขั้นต่ำ: token ต้องมีรูปแบบ/claims ที่ต้องใช้และเวลาหมดอายุสมเหตุผล จากนั้นตรวจหน้า authenticated และหน่วยงานที่เลือกจริง; การ decode ฝั่ง client ไม่ใช่การ verify signature หรือการยืนยันว่า server รับ session
- **ข้อผิดพลาดนี้ไม่ใช่หลักฐานว่าเป็นต้นเหตุ TS 027** ต้องแยกจากการทดสอบ ThaID

### F7 — P2: preview แทรกข้อมูลผู้ป่วยลง innerHTML โดยไม่ escape

- `app/templates/form.html:367–369` นำ summary ที่มีชื่อ/HN/AN จากข้อมูลเคสมาสร้าง HTML ด้วย template string
- ผลกระทบ: ข้อความที่มี markup ถูก browser ตีความเป็น HTML รวมถึง event handler ได้; เป็น source trace ไม่ได้ทดสอบโจมตีในแอปจริง
- แก้ขั้นต่ำ: สร้าง element แล้วใส่ `textContent` สำหรับค่าและ notes

## TS 027: สิ่งที่รู้และไม่รู้

- handoff ระบุว่าเอา token injection ออกแล้วยังพบ TS 027 จึงยังสรุปว่า injection เป็นสาเหตุไม่ได้
- ค้นเว็บด้วย ThaID + “TS 027” ในรอบนี้ไม่พบแหล่งทางการที่อธิบายรหัสดังกล่าว; ไม่ควรแต่งความหมายของ error
- Playwright ระบุ `chromium_sandbox` ค่าเริ่มต้น false, `channel="msedge"` เป็น browser channel ที่รองรับ และปิด persistent context จะปิด browser: [เอกสาร BrowserType](https://playwright.dev/python/docs/api/class-browsertype)
- โค้ดใช้งาน msedge อยู่แล้ว (`fill_nrefer.py:357–359`) การเสนอแค่เปลี่ยนเป็น msedge จึงไม่ใช่การทดลองใหม่ ส่วน sandbox flag มีคำอธิบายจากค่าเริ่มต้นแต่ยังไม่มีหลักฐานว่าเกี่ยวกับ TS 027
- ไม่ข้ามไป attach personal Edge profile หรือทำระบบค้างทั้งวันก่อนมีผลเปรียบเทียบ: จะเพิ่มตัวแปรและภาระการจัดการ session โดยยังไม่รู้สาเหตุ

## แผนตามลำดับ พร้อมเกณฑ์ผ่าน

### ด่าน 1 — แก้ความถูกต้องในเครื่อง

ทำ F1–F7 โดยเก็บ architecture เดิม เน้น F1/F2/F3/F5 ก่อน และแยก test DB/profile/store ตั้งแต่ต้น

เกณฑ์ผ่าน: ไม่มี production auto-save path; unrelated save ไม่เปลี่ยนสถานะเคส; HN หลาย AN ไม่เลือก ref ผิด; unknown ไม่กลายเป็น ID/เวลาแต่งขึ้น; resend ไม่ Add new; readback mismatch แจ้งชัด; duplicate queue ID ไม่ถูกประมวลผลซ้ำ; preview แสดง markup เป็นข้อความ

เพิ่มกรณี response สูญหาย/ผลบันทึกไม่แน่ชัด, HN ถูกผู้ใช้แก้ระหว่างตรวจ, HIS ตอบช้า, ช่องต้นทางว่างแต่ HIS มีค่า, token เสีย/หมดอายุ, ปิดหน้า และวัน พ.ศ./ค.ศ. ไม่ใช่เพิ่ม happy path ซ้ำ

### ด่าน 2 — แยกพิสูจน์ login เท่านั้น

ใช้ URL เดียว บัญชี/มือถือ/เครือข่ายเดียวกัน จดเวลาและผลแต่ละรอบ ไม่กรอกผู้ป่วย ไม่บันทึก token/code/QR ลง log

1. ให้ผู้ใช้สแกน ThaID ผ่าน Edge ที่เปิดตามปกติ เพื่อได้ baseline
2. ถ้า baseline ไม่ผ่าน: หยุดปรับ automation เก็บ error+เวลาไปตรวจบัญชี/แอป/บริการกับผู้ดูแลก่อน
3. ถ้าผ่าน: เปรียบเทียบ manual launch กับ Playwright โดยใช้ application profile ที่ปิดสนิทและสภาวะเริ่มต้นเทียบกันได้ ห้ามเปิดสอง instance ใช้ profile เดียวกัน
4. เมื่อ reproduce ความต่างได้ จึงเปลี่ยนทีละตัว: sandbox enabled; profile ใหม่สำหรับทดสอบ; session lifecycle ทีละขั้น เก็บว่าแต่ละรอบตัดสมมติฐานอะไรได้
5. attach/CDP หรือคงหน้าต่างทั้งวันพิจารณาเมื่อผลบอกว่าจำเป็น พร้อมตรวจวิธีรองรับจากเอกสารปัจจุบัน

เกณฑ์ผ่าน: login ผ่านด้วย flow ที่ผู้ใช้ใช้จริงได้ซ้ำ พร้อมหน้า authenticated/หน่วยงานถูกต้อง ไม่ใช่เพียงพบ token

### ด่าน 3 — ฟอร์มจริงแบบไม่เกิด record

เตรียมโหมดตรวจที่บล็อก request เขียนข้อมูลของ DMIS รวม save-person/save-patient และ operation เขียนอื่นที่สำรวจพบ ตั้งแต่ก่อนเปิดแบบฟอร์ม ตรวจระบบบล็อกใน mock ก่อน; allowlist เฉพาะการอ่านที่จำเป็น แยกจาก auth flow ให้ชัด

จากนั้นใช้ข้อมูลสมมติที่เจ้าของระบบอนุญาต ตรวจ datepicker พ.ศ./ค.ศ., เวลา, mRS 0–6, ward, radio, Dx/DMIS, อายุ/LOS ทั้งค่าบนหน้าจอและค่าที่ component รับ ผ่านวิธีที่ยืนยันได้โดยไม่ส่ง write request ไม่กดบันทึก แล้วปิดฟอร์ม เก็บผลรายช่องและจำนวน write ที่ถึง server ต้องเป็นศูนย์

ถ้าตรวจ model ไม่ได้ ให้บันทึกช่องนั้นว่ายังไม่ผ่าน ห้ามใช้การอ่าน input.value อย่างเดียวอ้างว่า Angular รับข้อมูลแล้ว

### ด่าน 4 — รับรองความหมายและ pilot

เจ้าของทะเบียนรับรอง CT/MRI, TIA/CVT, EMS, discharge, เวลาไม่ทราบ, ward mapping และนโยบายไม่มี AN ก่อนเปิดใช้งานจริง

เริ่มทีละเคสเมื่อด่านก่อนหน้าผ่าน ผู้ใช้ตรวจและเป็นคนกดบันทึกเองเท่านั้น; ตรวจทะเบียนว่าตรงคน/ครั้งรักษา/ref ก่อนเปิดคิวหลายเคส การบันทึกจริงเป็นขั้นแยกจากการทดสอบ no-write อย่างชัดเจน

## ลำดับที่แนะนำให้ทีมทำต่อ

แก้ save identity + resend + unknown mapping + เอา auto-confirm ออกจาก production เป็นชุดแรก จากนั้น readiness/readback/preview แล้วจึงเข้ารอบ login ที่มี baseline ชัดเจน วิธีนี้ทำให้แม้ ThaID ยังติด ทีมก็ปิดข้อผิดพลาดที่พิสูจน์ได้ไปก่อน โดยไม่วนเดาสาเหตุเดิม
