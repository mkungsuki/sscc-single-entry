# nRefer เฟส 2 — ผลตรวจเว็บและแผนแก้

วันที่ตรวจ: 11 กันยายน 2026 · เว็บแสดง `5.0.8-2026.08.07-1`

สถานะ: แผนจากโค้ดเว็บปัจจุบัน + หน้าฟอร์มเพิ่มใหม่จริง + scoped DOM ของแท็บ 4/5/8 หลังผู้ใช้อนุญาต; ยังไม่ใช่การรับรองตัวกรอกหรือการบันทึกจริง

## เป้าหมาย

กรอกข้อมูลหลัก → ให้พยาบาลพิมพ์ AN แล้ว HN และบันทึกเอง → เปิดรายการเดิมที่ยืนยันตัวตนและครั้งรักษาแล้ว → เตรียม BI และแผนจำหน่ายให้พยาบาลบันทึกเอง พร้อมสถานะแยกสามขั้นและทำต่อจากขั้นค้างได้

แนวทางที่เล็กที่สุดคือใช้ mapper, ตัวกรอก, observer, browser session และ custom fields เดิมต่อ เพิ่มขั้นตอนหลังบันทึกและการตรวจผล ไม่สร้างตัวเรียก API เขียนแทนหน้าเว็บ

### ขอบเขตจากการสำรวจงานพยาบาลที่ผู้ใช้แจ้งเพิ่มเติม

ผู้ใช้ระบุว่า “พยาบาล stroke กรอกเท่านี้นะที่รื้อดูมา” พร้อมภาพเฉพาะส่วนล่างห้าภาพ ให้ใช้เป็นขอบเขตการพัฒนาในรอบนี้ โดยไม่เก็บข้อมูลระบุตัวหรือคัดลอกค่าทางคลินิกของเคสตัวอย่างมาเป็น default

| ส่วน | หลักฐานที่เห็นในภาพ | ขอบเขตโปรแกรม |
|---|---|---|
| 4 ประเมินก่อนจำหน่าย | มีรายการประเมิน BI เดิมและแบบประเมิน 10 ข้อ | ทำตัวกรอก BI รายข้อ พร้อมวันเวลา/ผู้ประเมินและการตรวจคะแนน |
| 5 แผนจำหน่าย | มีรายการสถานพยาบาลปลายทางและช่อง impairment/needs/IMC/caregiver/complication/goal/detail | ทำตัวกรอกแผนตามข้อมูลต้นทาง; ส่วนปลายทางให้พยาบาลจัดการเองตามข้อตกลงเดิม |
| 6 เยี่ยมบ้าน | แสดงจำนวนรายการ 0 และปุ่มเพิ่ม | ไม่เพิ่มงานเยี่ยมบ้านให้ stroke unit ในรอบนี้ |
| 7 Motor power | หัวแบบฟอร์มยังแสดง “เพิ่ม” | ภาพนี้ไม่ยืนยันว่ามีรายการที่บันทึกแล้ว จึงยังไม่เพิ่ม ASIA เป็นขั้นบังคับหรือเติมคะแนนปกติอัตโนมัติ |
| 8 สิ้นสุดการติดตาม | แสดงสถานะอยู่ระหว่างการรักษา/ติดตาม | ไม่เพิ่มขั้นปิดติดตามอัตโนมัติ; สำหรับเคสเดิมคงสถานะจริง ห้าม reset จากตัวอย่าง |

ขอบเขตหลักจึงเป็น **ข้อมูลหลัก → BI ก่อนจำหน่าย → แผนจำหน่าย** ข้อสงสัยเฉพาะ Motor power ไม่บล็อกการทำแท็บ 4/5 ตามที่ผู้ใช้ระบุแล้ว

อัปเดตตามคำยืนยันล่าสุด: ทำ Motor power แบบ stroke 0–5 แยกแขนขาสี่ส่วน โดยคัดลอกแขน → C5–T1 และขา → L2–S1 ด้านเดียวกันเป็นค่าเริ่มต้นตามวิธีรายงานที่ผู้ใช้ระบุ แก้รายช่องได้และเก็บที่มาว่าเป็นค่าคัดลอก ไม่ต้องยืนยันรายท่าก่อนคัดลอก เพิ่ม UI และตัวกรอกแท็บ 7 แยกแล้ว ดูข้อกำหนดล่าสุดใน `stroke-motor-short-form-spec.md`; ยังไม่ใช่การทำ pipeline เฟส 2 ทั้งชุดเสร็จ

คะแนน BI, ช่อง needs ที่ถูกติ๊ก, Case IMC, ความพร้อมญาติ และสถานพยาบาลปลายทางในภาพเป็นค่าของตัวอย่าง ไม่ใช่คำสั่งให้ใช้ค่าเดียวกันทุกเคส ช่องว่างในภาพไม่ใช่หลักฐานว่าละฟิลด์นั้นได้ทุกเคส

- เปิดหน้า login จริง เห็นเวอร์ชันข้างต้น ผู้ใช้ล็อกอินให้แล้ว
- เปิดทะเบียนและ Add new จริง: ช่อง HN/AN ว่าง วันที่หลักเปิดใช้งานได้ วันที่ rt-PA/CT/SU ถูกปิดตาม radio ค่าเริ่มต้น; ปุ่มบันทึก disabled; ยังไม่มีแท็บ 4–8

- อ่าน source ของ component หลักและ component BI แล้วทดลองเมธอดจริงที่สกัดออกมาใน Node ด้วย service stubs/ข้อมูลสมมติ 10 กรณี ดู `repro_phase2_public.cjs` และ `public-phase2-20260911/repro-results.json`

- ทดลอง guard ปัจจุบันด้วย request จำลอง 12 กรณี: reference GET สองรายการผ่าน, POST อ่าน dmis-evaluate/hospcare/imc-evaluate ถูก block ทั้งสาม, คำขอเขียน/ลบที่ทดลองถูก block ทั้งหมด ดู `public-phase2-20260911/guard-probe.json` (ไม่มี network หรือ DB)
- การอ่านรายละเอียดเคสหลัง login เคยถูก automatic approval review หยุดไว้ ต่อมาผู้ใช้อนุญาตเฉพาะส่วนล่างและห้ามเห็นชื่อ/HN/AN จึงเปลี่ยนเป็น scoped read-only evaluate ที่คืนเฉพาะ field metadata/reference options ก่อนส่งถึงโมเดล ตรวจแท็บ 4/5/8 สำเร็จภายใต้ขอบเขตนี้ ไม่อ่านข้อมูลระบุตัวหรือค่าของเคส ดู `safe-inspection-scope.md`

## 2. จุดที่ต้องแก้ความเข้าใจจากบรีฟก่อนเขียนโค้ด

### 2.1 บันทึกเคสใหม่ไม่ได้เปิดแท็บถัดไปให้อัตโนมัติ

`savePatient()` กรณี `editRow.ref == 0` ส่ง `onDataChange({saved:1})`; parent เรียก `getPatient()` แล้วตั้ง `activeTab='search'` ส่วนกรณีมี ref อยู่แล้วจึงเรียก `getStrokePatient(1)`

ดังนั้น barrier แบบรอ `pk-tabs + dmis-disc-evaluate` อย่างเดียวจะรอไม่จบ ต้องมีขั้น **ค้นและเปิดรายการที่เพิ่งบันทึก** ก่อน ห้ามใช้แถวแรกหรือ ref สูงสุดเป็นตัวตัดสิน ตัวกรองวันที่เดิมอาจไม่ครอบคลุมเคสที่เพิ่มด้วย

### 2.2 hospcare เขียนเมื่อกด +Add หลังเลือก

parent template ของ dropdown เปลี่ยนค่า `hosp_destination` / `pcu_destination` ผ่าน ngModel เท่านั้น จากนั้นแสดง `+Add` ซึ่งผูก `addHospcare(destination)`; เมธอดนี้จึงเรียก `save-hospcare` โดยไม่ผ่านปุ่มบันทึกแผนจำหน่าย

แก้ข้อความในบรีฟให้ตรงกลไก แต่ยังคงขอบเขตเดิม: โปรแกรมไม่แตะพื้นที่จังหวัด/โรงพยาบาล/PCU/+Add/ลบ ให้พยาบาลจัดการเอง

### 2.3 BI ที่ render จริงไม่ได้มีทุกช่องตามบรีฟ

`dmis-disc-evaluate` มีวันที่ เวลา ผู้ประเมิน radio คะแนน BI รายข้อ และ detail โดย payload มี evaluate_id, patient_ref, evaluate_type, date, score, detail, evaluate_name, input_id, choice/evaluate

ไม่พบ mRS, complication หรือ next_goal ในฟอร์มและ save payload ของ component นี้ จึงไม่สร้าง locator สมมติให้ช่องเหล่านั้น mRS อยู่ในฟอร์มหลัก ส่วน complication อยู่ในแผนจำหน่าย ส่วน component เยี่ยมบ้านมีโครงสร้างอื่น อย่านำมาปนกัน

### 2.4 selector ของ BI ต่างจาก IMC และต้องยึด DOM จริง

- Case IMC: value 0 และ 2 ใช้ id ซ้ำ `editRow.imc0` ใน template
- radio BI ใน DOM จริงไม่มี name/value attributes; value property เป็น `on` และ id ซ้ำในข้อเดียวกัน เช่น `currentVisit_evaluate_feeding` ทุกตัว การเห็น name/value binding ใน Angular template ไม่ได้แปลว่ามี attributes ใช้ค้นได้จริง
- BI ต้องใช้ component → `.evaluate-choice` ที่หัวข้อ/key ตรง schema → span ที่ข้อความตัวเลือกตรง → radio และ assert ว่าพบหนึ่งตัว; ตรวจ checked หลังกรอกโดย local worker ไม่ใช้ id หรือ name+value
- IMC/caregiver ใช้ component scope + `input[name=...][value=...]` ได้ ยืนยัน attributes จริงแล้ว
- caregiver ยืนยันค่าได้แล้ว: `1=พร้อม`, `0=ไม่พร้อม`

### 2.5 BI คะแนนศูนย์มีความเสี่ยงในโค้ดเว็บ

ทดลองเมธอดจริงกับข้อมูลสมมติแล้ว:

1. เปิดรายการเดิมที่คะแนนข้อหนึ่งเป็นตัวเลข `0`: `value || max_score` เปลี่ยนเป็นคะแนนสูงสุด แต่สตริง `"0"` ไม่เปลี่ยน ต้องตรวจชนิดข้อมูล response จริงก่อนสรุปว่าทุกเคสได้รับผล
2. บันทึกคะแนนรวม `0`: `sum_score || old_score` ทำให้ payload ไม่มี score หากไม่มีค่าเก่า หรือใช้คะแนนเก่าที่ไม่ใช่ 0

ห้ามเปลี่ยน 0 เป็นคะแนนอื่นเพื่อให้ผ่าน และห้ามอ้างว่า readback หน้าจอผ่านแล้วเท่ากับ payload ถูก ต้องมีกรณีทดสอบศูนย์ใน UI → request → response/readback หลังโหลด และถือเป็นเงื่อนไขค้างก่อนรับรอง BI คะแนนศูนย์ ไม่แก้ Angular model ภายในหรือยิง API บันทึกแทน

### 2.6 no-save เคสใหม่วิ่งครบสามขั้นในเว็บจริงไม่ได้ด้วยตัวเอง

บล็อกการสร้าง record แล้วจะไม่มี ref เปิดแท็บหลังบันทึก การพิสูจน์ต้องแยก:

- เคสสมมติใหม่: ตรวจฟอร์มหลักแบบ no-save
- แท็บ 4/5: ตรวจโครงสร้างจากเคสที่ได้รับอนุญาต; ถ้าจะทดสอบกรอกต้องมีกรณีทดสอบที่อนุญาตและ guard ครบก่อน
- ทดสอบ flow สร้าง→เปิดรายการ→BI→แผน ด้วย mock/local
- พิสูจน์การบันทึกครบจริงผ่าน pilot ที่พยาบาลเป็นผู้กดทุกขั้น

## 3. แผนงานตามลำดับ

### P0 — HN/AN และฟอร์มหลัก (ทำได้ทันที ไม่รอขอนแก่น)

ไฟล์: `app/nrefer_ui.py`, `app/fill_nrefer.py`, `app/mock/test_nrefer_cases.py`

1. ยกเลิกการกรอก HN/AN อัตโนมัติ และไม่คาดว่าคู่นี้ต้องตรงใน readback ก่อนส่งต่อให้คน ส่วน identity ที่ observer ใช้ยังมาจากข้อมูลต้นทางครบทุกตัวอักษร
2. ก่อนกรอกตรวจ HN/AN ว่างและ readiness ของช่องวันที่หลัก เช่น birth/admit; ไม่เอาช่องที่ radio ตั้งใจ disable มาตัดสินว่า loading ค้าง
3. กรอก Dx → ข้อความ/ตัวเลข → radio → วันที่ → เวลา → mRS/ward → final readback; ตรวจ mRS/ward อีกครั้งตอนท้ายด้วย ไม่พึ่งเฉพาะการตรวจทันทีหลังเลือก
4. แยกความผิดพลาดที่ต้องหยุดออกจากคำเตือนข้อมูลขาด ถ้าวันที่หลักยัง disable เกินเวลาที่กำหนด ให้หยุดพร้อมเหตุ ไม่วน timeout ทุกช่อง
5. เปลี่ยนจุด focus/blur ใน helper วันที่ให้ใช้ control ที่ไม่ใช่ HN/AN เพื่อลดการพึ่งช่อง identity
6. แถบแสดงครบ: ตรวจวันเวลา/mRS/ward ก่อน, AN แล้ว HN พร้อมค่าก๊อปที่คงศูนย์นำหน้า, อาการหมุนค้างที่ทราบจาก HIS, และถ้า lookup เปลี่ยนค่า/AN หายให้หยุดตรวจ ไม่แสดงคำว่า “ปกติ” เหมารวมทุก error
7. สีเขียวหมายถึงข้อมูลที่โปรแกรมรับผิดชอบผ่านแล้วและรอพยาบาล ไม่ใช่ “บันทึกสำเร็จ”

เทสต์: HN/AN ไม่ถูกพิมพ์, ศูนย์นำหน้าไม่หาย, required date disabled ต้อง fail fast, optional date disabled ไม่ fail ผิด, banner ครบ, observer รับเฉพาะ identity ที่ตรงหลังคนพิมพ์, mismatched AN ไม่สำเร็จ

### P1 — เก็บ schema ที่มีหลักฐาน

ไฟล์ใหม่ที่เสนอ: `app/schema/nrefer_contract.json`, `app/schema/nrefer_bi_choices.json`

- ชื่อ care needs 15 ข้อ, impairment 5 ข้อ, ค่า IMC/caregiver ยืนยันจาก template แล้ว เก็บใน `public-phase2-20260911/verified-contract.json`
- เก็บ UI-rendered BI reference แล้ว: name จาก label, caption, seq, choices display/score ตามข้อความที่เว็บแสดง; ยังต้องเทียบ raw evaluate-choice response ผ่านวิธีที่ไม่ส่ง token/ข้อมูลเคสถึงโมเดลก่อนปิดเกณฑ์ API-schema ตามบรีฟ
- เก็บ service-status จากรายการตัวเลือกจริงแยกแล้ว; ไม่อ่านหรือเปลี่ยนสถานะจบติดตามของเคส
- ระบุ version, capture date, source และ validation; reject schema ที่ไม่มีครบ 10 ข้อ/คะแนนไม่ใช่ตัวเลข/ตัวเลือกซ้ำผิดปกติ
- ไม่เดา BI จากคะแนนรวม และไม่ hardcode ตัวเลือกมาตรฐานจากความจำ

### P2 — ฟอร์มต้นทางก่อนจำหน่าย

ไฟล์: `custom_fields_defaults.json`, `case_form.py`, `templates/form.html`, validation ใน server/mapper

- ใช้ stored keys `cf_bi_*`, `cf_imp_*`, `cf_need_*`, `cf_imc`, `cf_caregiver`, `cf_goal` ตามบรีฟ; เพิ่มวันที่/เวลา/ผู้ประเมินและ detail ที่จำเป็นโดยไม่เปลี่ยน key เดิม
- จัดหมวด BI และแผนใกล้ข้อมูลก่อนจำหน่ายจริง ไม่กองท้ายฟอร์ม
- BI เริ่ม “ยังไม่ประเมิน” ไม่ default max; ครบทุกข้อจึงรวมเข้า `x_b10`; ถ้าค่าเดิมไม่ตรงให้ผู้ใช้ตัดสินใจ
- checkbox ต้องแยก “ตรวจแล้วไม่มี” ออกจาก “ยังไม่ประเมิน” เช่นใช้ review marker ประจำหมวด; ห้ามตีความฟอร์มว่างว่าไม่มี impairment/need
- IMC/caregiver เริ่มไม่ระบุ จนเจ้าของงานยืนยัน default; ไม่ปล่อยค่า 0 ของเว็บผ่านเป็นข้อมูลที่พยาบาลตัดสินแล้ว
- default ผู้ประเมินต้องมาจากผู้ login nRefer ที่รู้จริงหรือผู้ใช้กำหนด; โปรแกรม SSCC ปัจจุบันไม่ควรสมมติว่ามีชื่อผู้ login ของตนเอง
- คงข้อห้าม mapping UTI→CA_UTI, pressure sore โดยไม่มี grade, x_c11→swallowing problem และ B4.1→hospcare

### P3 — สถานะแยกขั้นและการเปิด record เดิม

ไฟล์: `db.py`, `server.py`, `browser_session.py`, `fill_nrefer.py`, UI สถานะ

- มี `nrefer_main`, `nrefer_bi`, `nrefer_plan` แต่ละขั้นใช้สถานะ not_started / prepared / awaiting_user / saved / uncertain ตามจำเป็น พร้อม timestamp และ fingerprint ข้อมูลต้นทางที่เตรียม
- เก็บ patient ref แยกจาก evaluate_id; BI หนึ่งครั้งมีตัวระบุประเมินของตนเอง
- migrate สถานะเก่าเป็น main เท่านั้น; BI/plan ยังไม่ยืนยัน ห้ามตั้ง saved ทั้งหมด
- หลัง save main ให้จับผลสำเร็จที่ผูก identity แล้วเปิดทะเบียน ค้น HN/AN และตรวจหน่วยงาน+ครั้งรักษา+วันที่จนได้รายการเดียว จึงกดเปิดผ่าน UI และผูก ref ที่ตรวจได้จากการโหลดรายการนั้น
- หากไม่เจอ/เจอหลายรายการ/ยังไม่รู้ ref: main ยังคง saved ถ้ามีหลักฐานสำเร็จ แต่ขั้นถัดไปเป็น needs_review ไม่เลือกแทนโดยเดา และไม่ Add new ซ้ำ
- resume BI/plan ต้องผ่านเส้นทางเปิดรายการเดิม; ยกเลิก guard แบบเหมารวมที่ปิดทุกงานทันทีเมื่อมี `nrefer_ref`
- หาก source เปลี่ยนหลังเตรียมหรือส่งแล้ว ให้แสดงต้องทบทวนเฉพาะขั้นที่เกี่ยวข้อง; ไม่เปลี่ยนหลักฐานว่าเคยบันทึกแล้วเป็นไม่เคยบันทึก

### P4 — ตัวกรอก BI และแผน + observer

ไฟล์ใหม่ที่เสนอ: `nrefer_discharge.py`; ขยาย `nrefer_save.py` และ mock DOM

**BI**

- เปิดแท็บ 4; สำรวจรายการประเมินก่อน ถ้ามีรายการเดิมที่ตรงเป้าหมายให้เข้าสู่ทางแก้รายการนั้น ไม่กด Add new ทุกครั้งที่ resume
- ใช้ `+ Add new` ปกติเมื่อยืนยันว่าต้องสร้างใหม่ ไม่ใช้ `copy last`
- กรอกวันที่/เวลา/ผู้ประเมิน/10 radio/detail และ readback ทุกข้อรวม total
- ไม่ปล่อยต้นทางว่างผ่านด้วย default max; ปัญหาคะแนนศูนย์ต้องถูกตรวจและแสดงเหตุ ไม่ส่งต่อพร้อมเครื่องหมายผ่าน
- observer ผูก endpoint `save-dmis-evaluate`, patient_ref, evaluate_type='discharge', identity หน่วยงาน, evaluate_id ถ้ามี และตรวจคะแนน/ข้อที่ส่งเทียบกับ snapshot ที่พยาบาลตรวจ
- HTTP 200 อย่างเดียวไม่พอ; ต้องตรวจ business status และข้อมูลที่สัมพันธ์กับขั้นนี้
- เมื่อ request เริ่มแล้วผลขาดหายให้ uncertain; ก่อน retry ตรวจรายการประเมินเดิมเพื่อกันสร้างซ้ำ

**แผนจำหน่าย**

- เปิดแท็บ 5; เติมเฉพาะ impairment, needs, IMC, caregiver, complication ที่ยืนยันความหมายแล้ว, goal/detail
- ใช้ scoped selector name+value โดยเฉพาะ IMC ที่ id ซ้ำ
- readback checkbox ทั้ง true และ false, radio, autocomplete และ text ให้ครบ
- บันทึกแผนเรียก `savePatient()` ทั้ง record รวมข้อมูลหลัก ไม่ใช่ patch แค่แผน: ต้องตรวจว่าข้อมูลหลัก/identity ยังตรงและไม่ถูกทำหาย ก่อนให้พยาบาลกด
- observer plan ต้องเริ่มช่วงแผนและผูก ref เดิม+ข้อมูลแผน ไม่เผลอนับ response main รอบก่อนเป็น plan สำเร็จ
- ให้พยาบาลเลือกปลายทางและกด +Add เอง; แยกข้อความ “แผนบันทึกแล้ว” ออกจากสถานะปลายทางซึ่งยังไม่ได้ยืนยัน

### P5 — guard และเกณฑ์ยอมรับ

`nrefer_guard.py`: คง deny-by-default เพิ่มเฉพาะ read methods ที่ตรวจแล้ว ได้แก่ POST dmis-evaluate / hospcare / imc-evaluate ซึ่งจำเป็นแม้แต่การโหลดรายการ; reference GET evaluate-choice / service-status มีอยู่แล้ว

- พิสูจน์ว่า save-person/save-patient/save-dmis-evaluate/save-hospcare/save-imc-evaluate/save-visit* และ delete ทุกชนิดยังถูก block ใน no-save
- ทำ mock การกลับทะเบียนหลัง save ใหม่, record ไม่อยู่ในช่วงวันที่, หลาย admission, response ไม่มี ref, BI default max, numeric 0/string 0, retry หลังบันทึกค้าง, IMC id ซ้ำ และแผนที่ save ทั้ง record
- มี tripwire ที่พื้นที่ hospcare ให้เทสต์ fail ทันทีหากตัวกรอกเปิด/เลือก dropdown หรือกด +Add
- เพิ่ม test DOM ของ BI ที่ไม่มี name/value attributes และใช้ id ซ้ำ เพื่อกัน mock ที่สะดวกกว่าหน้าเว็บจริง
- ทดสอบหลักฐานหลัง user-save แยกจาก prepared readback; ไม่ใช้ toast หรือกดปุ่มได้เป็นหลักฐานว่าบันทึกถูกต้อง
- รัน live no-save ฟอร์มหลักด้วยข้อมูลสมมติ จากนั้นให้พยาบาลพิมพ์ AN/HN ตรวจค่าที่ยังคงอยู่และปุ่ม Save แล้วปิดโดยไม่บันทึก
- pilot หนึ่งเคสที่พยาบาลกด Save เองทุกขั้น และตรวจทะเบียน/ประเมินที่โหลดกลับให้ HN/AN/date/BI/plan ตรง จึงยอมรับงาน

## 4. คำถามที่ยังต้องได้ข้อสรุปจากเจ้าของงาน

1. ผู้ใช้ให้ขอบเขตงานจริงของพยาบาลแล้ว: ทำแท็บ 4+5; เหลือเฉพาะข้อยืนยันเพิ่มเติมหากภายหลังต้องการรวมแท็บ 7 ซึ่งภาพที่ส่งยังเป็นหน้าเพิ่ม ไม่บล็อกงานแท็บ 4+5
2. ใครตัดสิน Case IMC และตั้ง default ได้หรือไม่
3. ใครรับผิดชอบ hospcare และต้องเสร็จตอนจำหน่ายหรือภายหลัง
4. นิยาม complication และ grade ที่จะใช้จากต้นทาง
5. BI มีการประเมินก่อนจำหน่ายซ้ำกี่ครั้ง และการ resume ของโปรแกรมควรแก้ครั้งใด

คำถามที่เหลือไม่บล็อกการพัฒนาช่องกรอกและ workflow ตามขอบเขตที่ผู้ใช้แจ้ง แต่ยังห้ามกำหนดค่าคลินิก/default แทนผู้ใช้โดยไม่มีข้อสรุป
